# /작업 — 지시→작업→직접 확인→빌드·커밋·푸시 (배포는 확인 후)

**발동**: `/작업 <지시>`. 형이 시킨 일을 수행하고 **완료 후 직접 확인·푸시**까지 간다.
**철칙**: 🔴 **운영 VM 배포는 절대 자동으로 하지 않는다** — 빌드·테스트 그린·푸시까지만 자동, 배포는 형이 "배포"라고 할 때만.
**⛔2026-09-14 형 지시**: 자동 검사 에이전트(`/검사` 4종)·제시·코난을 붙이지 않는다. 확인은 안토니가 명령을 직접 돌린 결과로 한다(CLAUDE.md §14).

## 단계 (순서대로, 각 단계 통과해야 다음)

### 1) 작업 수행
- 지시를 안토니가 직접 수행. 3개↑ 파일·신규기능·API/DB 변경이면 먼저 계획을 한 줄씩 형에게 말하고 진행. 기존 작업 보존·외과적 수정.
- 무엇을 준비하는지·무엇을 돌리는지 짧게 계속 알린다(침묵 금지).

### 2) 직접 확인 — 에이전트 없이
- 바꾼 파일을 다시 열어 의도대로 됐는지, 빠진 곳이 없는지 확인한다.
- 실패하면 원인을 짚어 고치고 다시 확인한다. **같은 실패가 두 번이면 방법을 바꾸거나 형에게 한 줄로 보고**한다.

### 3) 빌드·테스트 (증거 기반)
```bash
# 프로젝트에 맞게: 예) wssc-unified
cd <앱경로> && npx vitest run 2>&1 | tail -5 && npm run build 2>&1 | tail -5
```
- 실패 시 에러를 직접 고친 뒤 재실행. **0 실패 + 빌드 성공** 증거 확보해야 다음.

### 4) 커밋·푸시
- **계정 정합 먼저**: repo owner 확인 → `gh auth switch --user <owner>`(yyplus·hanwool·cleancare=ttong0627 / 물류·웰쉐어=ttong627).
- 의미있는 커밋 메시지(`feat:`/`fix:` 등 + 무엇을·왜). 변경 전체를 `git add` 신중히(데이터 폴더·시크릿 제외).
- `git push origin main`(또는 현재 브랜치). 푸시 결과 확인.

### 5) 배포 게이트 (멈춤)
- 여기서 **멈추고** 형에게 보고:
  ```
  ✅ 확인 완료 · 테스트 N개 그린 · 빌드 성공 · 푸시 완료(<hash>).
  운영 배포(http://34.50.53.232)하려면 "배포"라고 하세요.
  ```
- 형이 "배포"라고 하면 그때 VM 배포(`vm-deploy.sh`) 실행. 그 전엔 절대 배포하지 않는다.

## 컨텍스트 관리 (대화 길어지면)
- 컨텍스트 **50% 도달**이 느껴지면 단계 사이에서 **`/핸드오프`**로 진행상황·결정·다음 단계를 `HANDOFF.md`에 저장하고, 형에게 "새 세션에서 '이어서'로 계속하세요"라고 안내한다. (하니스 자동요약과 병행 — 끊겨도 복원 가능하게.)

## 핵심
- 작업→직접 확인→빌드·테스트→푸시는 자동, **배포만 형 확인**. 검사 에이전트는 형이 「검사해」라고 할 때만. 증거 없는 완료 선언 금지.
