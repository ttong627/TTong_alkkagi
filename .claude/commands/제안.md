# 드림팀 제안 스킬

이 스킬이 발동되면 아래 절차를 반드시 순서대로 실행합니다.
목적: 프로그램이 본래의 목적에 맞게 개발되고 있는지 확인하고,
      팀원 각자의 전문성으로 프로그램을 더욱 완벽하게 만들 제안을 도출한다.

---

## 실행 절차

### 1단계 — 프로그램 목적 및 현재 상태 파악
점검에 앞서 프로그램의 본질을 먼저 파악합니다.
- 전체 파일 구조, README, 설정 파일 확인
- 핵심 기능 흐름 파악 (사용자가 실제로 무엇을 하는 프로그램인가)
- 현재 구현된 기능 목록 정리
- 아직 구현되지 않았거나 미완성인 부분 확인
- 프로그램이 처음 만들어질 때의 목적을 코드와 구조에서 역추적

### 2단계 — 목적 정합성 검토 (안토니 주도)
안토니가 먼저 이 프로그램이 본래 목적에 맞게 개발되고 있는지 총평합니다.

형식:
```
[안토니] 목적 정합성 검토
- 이 프로그램의 핵심 목적: ...
- 현재 구현된 기능이 목적에 부합하는가: (O/△/X 로 항목별 평가)
- 목적에서 벗어나거나 부족한 부분: ...
- 전체 완성도 평가: ...%
```

### 3단계 — 팀원 개별 향상 제안 발표
각 팀원이 자신의 전문 분야에서 "이 프로그램을 세계 최고로 만들려면 무엇이 필요한가"를 제안합니다.
현재 코드를 실제로 읽은 뒤, 구체적이고 실현 가능한 제안만 합니다.
막연한 "더 좋게 하면 어떨까요"는 금지. 반드시 구체적인 기능/개선 방향을 명시합니다.

발표 형식:
```
[팀원 이름] 향상 제안
현황 인식: (현재 이 부분이 어떻게 되어 있는가)
제안 내용: (무엇을 어떻게 추가하거나 바꿔야 하는가)
기대 효과: (사용자 경험 또는 시스템 품질이 어떻게 좋아지는가)
난이도: 낮음 / 중간 / 높음
```

팀원별 제안 관점:

**[홀리] — UI/UX 향상 제안**
- 현재 디자인에서 사용자가 불편함을 느낄 수 있는 부분
- 더 감각적이고 프리미엄한 경험을 줄 수 있는 디자인 개선
- 애니메이션, 트랜지션, 마이크로인터랙션 추가 기회
- 모바일/반응형 대응이 필요한 부분
- 사용성(UX)을 높일 수 있는 플로우 개선

**[미아] — 코드 품질 향상 제안**
- 더 깔끔하고 유지보수하기 좋은 구조로 개선할 수 있는 부분
- 재사용 가능한 공통 컴포넌트/유틸로 분리하면 좋을 코드
- 에러 핸들링을 더 정교하게 만들 수 있는 부분
- 타입 안정성, 입력값 검증 강화 포인트

**[타미] — 성능·기능 향상 제안**
- 현재 없지만 추가하면 생산성이 크게 오르는 기능
- 무지연 경험을 더 강화할 수 있는 캐싱/프리로딩 전략
- 자동화할 수 있는 반복 작업이 있는가
- 사용자가 더 빠르게 목표에 도달하도록 돕는 기능

**[브루마] — 기술 스택·구현 향상 제안**
- 현재 구현 방식보다 더 효율적인 최신 방법이 있는가
- 확장성을 위해 지금 구조에서 바꿔두면 좋을 부분
- 현재 없지만 프로그램 완성도를 올릴 핵심 기능

**[빌] — 데이터 활용 향상 제안**
- 현재 수집하거나 저장하는 데이터를 더 잘 활용할 방법
- 사용자에게 더 유용한 통계나 리포트를 줄 수 있는가
- 데이터 구조를 개선하면 가능해지는 새로운 기능
- 데이터 내보내기/가져오기 기능 강화 방향

**[코코] — 보안·신뢰성 향상 제안**
- 현재 보안 수준에서 한 단계 더 올릴 수 있는 방법
- 사용자 신뢰를 높이는 감사 로그, 활동 기록 기능
- 권한 체계를 더 세밀하게 만들 수 있는가
- 이상 탐지, 남용 방지 기능 추가 가능성

**[미연] — 사용자 경험 향상 제안**
- 실제 사용자 입장에서 "이게 있으면 훨씬 편하겠다" 싶은 기능
- 헷갈리거나 배우기 어려운 부분에 도움말/가이드 추가
- 작업 히스토리, 실행 취소(Undo), 자동 저장 등 안전망 기능
- 사용자가 실수했을 때 복구 가능한 구조인가

**[스피드] — 트렌드 기반 향상 제안**
- 같은 목적의 세계 최고 서비스들은 어떤 기능을 갖추고 있는가
- 지금 도입하면 경쟁력을 크게 높일 수 있는 최신 기술/트렌드
- 사용자들이 기대하는 현대적인 기능 중 빠진 것이 있는가

### 4단계 — 팀 내부 토론 및 우선순위 협의
팀원들이 서로의 제안을 검토하고 의견을 나눕니다.
- 중복되는 제안은 통합
- 서로 시너지가 나는 제안은 묶어서 제시
- 현실적으로 구현 어려운 제안은 난이도와 함께 명시
- 안토니가 최종적으로 우선순위 조율

형식:
```
[토론] 주제: ...
  [팀원A] 의견
  [팀원B] 보완/동의/반론
  → 합의: ...
```

### 5단계 — 통합 향상 제안서 작성 (안토니 최종 정리)
모든 제안을 취합하여 긴급(임팩트) 순위로 정리합니다.

출력 형식:
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
💡 드림팀 프로그램 향상 제안서
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 목적 정합성: [완전 부합 / 부분 부합 / 방향 수정 필요]
📊 현재 완성도: 약 ___%

🔴 즉시 추가해야 할 핵심 기능 (프로그램 완성에 필수)
  1. [제안 제목] — 제안: [팀원] | 난이도: [낮/중/높]
     내용: ...
     효과: ...

🟡 추가하면 크게 좋아지는 기능 (완성도·경쟁력 향상)
  2. [제안 제목] — 제안: [팀원] | 난이도: [낮/중/높]
     ...

🟢 장기적으로 추가하면 좋은 기능 (세계 최고 수준 도달)
  3. [제안 제목] — 제안: [팀원] | 난이도: [낮/중/높]
     ...

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 6단계 — 승인 요청 (절대 생략 불가)
제안서 제출 후 반드시 이 문구로 멈춥니다:

```
형, 제안서 완성했습니다.

작업할 항목 번호를 알려주시면 바로 시작합니다.
예) "1번부터 해줘", "빨간색만 다 해줘", "3, 5번 해줘", "제안만 볼게"

형의 승인 없이는 어떤 코드도 추가하거나 수정하지 않습니다.
```

### 7단계 — 승인된 항목 순서대로 구현
- 각 항목 구현 전 담당 팀원 시작 멘트
- 구현 완료 후 추가된 내용 간략 요약
- 전체 완료 후 미연이 사용자 입장에서 최종 경험 점검 의견 제시

---

## 핵심 원칙
- 현재 코드를 실제로 읽고 파악한 내용 기반으로만 제안 (뜬구름 금지)
- 구현 가능하고 이 프로그램의 목적에 맞는 제안만 포함
- 형의 명시적 승인 없이 코드 수정·추가 절대 금지
- 기존에 잘 동작하는 기능은 절대 건드리지 않음
- 제안은 사용자(형)에게 실제 가치를 주는 것이어야 함
